# 배포 준비 진행 기록

확인일: 2026-10-03 · 기준: `af7e512` 이후의 배포 준비 작업 · [배포 전략](../2026-09-29/DEPLOYMENT_STRATEGY.md)

| 작업 | 상태 | 확인 결과·남은 조건 |
|---|---|---|
| D-01 운영 기준선 | 진행 중 | 저장소 `supabase/config.toml`의 프로젝트 ref는 현재 CLI 계정의 프로젝트 목록에 없다. 운영 DB 적용 이력을 읽지 못했다. 예시 URL `https://signalcar.lovable.app`은 다시 404였다. GitHub Deployments 기록은 없고, Lovable의 실제 Publish URL·활성 SHA는 미확인이다. |
| D-02 복구·비밀값 | 일부 확인 | 추적 중인 `.env`와 그 Git 이력 1개 버전에서 알려진 서비스 역할·메일·공공 API 비밀값 할당은 발견되지 않았다. 이는 전체 저장소 비밀값 검사나 유출 부재의 증거는 아니다. 운영 백업·Storage 객체 정책은 미확인이고 GitHub Secrets 목록은 현재 권한에서 403이다. 실제 키 값은 이 문서에 기록하지 않는다. |
| D-03 코드·DB CI | CI 완료·Publish 관문 대기 | [최신 GitHub Actions 실행](https://github.com/c-yeonwoo/signalcar/actions/runs/37118769506)에서 `npm ci`, 타입 검사, 앱 빌드, Bun 고정 설치, 단위 테스트 8개, 수집 CLI 번들, 격리 DB 마이그레이션 26개와 SQL 권한·데이터 계약 테스트 9개가 모두 통과했다. Lovable Publish가 이 검사 결과에 자동 연동된 것은 아니므로 릴리스 담당자가 통과 SHA를 확인해야 한다. |
| D-04 스테이징 | 미착수 | 분리된 Supabase/Lovable 환경이 확인되지 않았다. 실제 고객 데이터로 대체하지 않는다. |
| D-05 운영 DB 적용 경로 | 대기 | 현재 계정으로 운영 DB 이력·자동 적용 여부를 확인할 수 없다. `db push`는 실행하지 않았다. |
| D-06 운영 릴리스 | 대기 | 실제 URL·DB·백업과 스테이징 검증 후 진행한다. `main` 반영을 Publish 완료로 표시하지 않는다. |
| D-07 수집 워커 | 수동 미리보기만 가능 | Bun 버전·잠금 파일 설치·오류 종료 코드와 비활성 잡 강제 실행 금지를 적용했다. GitHub가 워크플로 수정 후 상태를 `active`로 바꿨으므로 예약 트리거와 운영 DB 비밀값을 전달하는 잡을 제거했다. 운영 수집은 실행되지 않았다. |

## 확인한 위험과 조치

- 원래 `package-lock.json`이 `package.json`과 맞지 않아 깨끗한 체크아웃의 `npm ci`가 실패했다. 잠금 파일을 동기화하고 PDF 의존성 버전을 검증한 조합으로 고정했다.
- 전체 ESLint는 기존 코드의 포맷팅을 포함해 1,860건의 경고·오류를 출력한다. 지금 모든 파일의 포맷을 바꾸지 않고, CI는 타입·테스트·빌드·DB 계약을 차단 관문으로 삼았다. lint 정리는 별도 변경으로 진행한다.
- 기존 수집 워크플로는 의존성 설치 없이 Bun `latest`를 사용했고, 수동 `--force`로 비활성 작업을 실행할 수 있었다. 현재 워크플로에는 예약 트리거와 운영 비밀값이 없으며, 수동 실행은 `--dry --no-claim` 미리보기만 허용한다. CLI의 `--force`도 거부한다.
- 워크플로 변경 후 GitHub 상태가 `disabled_inactivity`에서 `active`로 바뀌었다. CLI 계정의 `gh workflow disable` 요청은 저장소 admin 권한 부족(403)으로 거부됐다. 예약 트리거를 코드에서 제거해 실행 경로를 차단했다.
- SQL 테스트는 **별도 임시 로컬 Supabase 프로젝트**에 26개 마이그레이션을 처음부터 적용해 통과시켰다. 운영 DB와 기존 로컬 프로젝트의 데이터를 변경하지 않았다.

다음 관문은 실제 Lovable 프로젝트/Publish URL과 운영 Supabase 접근 확인, 마이그레이션 이력 대조, 백업·Storage 복구 연습이다. 이 세 가지가 확인될 때까지 운영 DB 적용·Publish·수집 재개는 대기한다.
