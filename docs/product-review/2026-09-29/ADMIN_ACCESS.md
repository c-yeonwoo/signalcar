# SC-009 · 관리자 권한 분리 결과

2026-09-29에 저장소 기준 권한 경로를 수정했다. `profiles.is_admin`은 계속 서버가 부여하는 플래그로 사용하며, 로그인한 사용자는 본인 `nickname`만 수정할 수 있다. 관리자 화면은 DB의 `is_admin=true`를 확인하며 이메일 목록이나 설정 누락을 권한으로 해석하지 않는다.

## 변경과 확인

| 항목 | 결과 |
|---|---|
| 신규 마이그레이션 | `supabase/migrations/20260929010000_lock_profile_admin_flag.sql`: 사용자 역할의 프로필 테이블 전체 INSERT/UPDATE를 회수하고 허용 열만 재부여. 익명의 `is_admin()` 실행도 회수 |
| 화면 | `src/routes/admin.tsx`: 입구와 로그인 계정 변경 후 화면에서 같은 DB 플래그를 확인. 조회 실패 시 접근 거부 |
| 사용하지 않는 설정 | `VITE_ADMIN_EMAILS`의 코드·예시·안내 제거 |
| 인증 URL 타입 | `/auth` 검색값을 선택 사항으로 정의해 선택값이 없는 로그인 링크와 리다이렉트를 타입 검사 통과 |
| 격리 DB 검증 | 기존 16개 SQL과 새 마이그레이션을 순서대로 적용. `supabase/tests/admin-access.sql` 실행 성공: 일반 계정 관리자 플래그 UPDATE/INSERT 거부, 닉네임 수정 허용, 관리 데이터 쓰기 거부, 서버 부여 관리자 쓰기 허용. 테스트 트랜잭션은 ROLLBACK |
| 코드 검사 | `npx tsc --noEmit`, 변경한 관리자·인증 라우트 ESLint, `npm run build` 통과 |

## 운영에 적용할 때 확인할 것

마이그레이션은 기존 `is_admin=true` 값을 자동으로 변경하지 않는다. 기존 값을 믿기 전에 권한 있는 운영자가 관리자 명단과 실제 계정 ID를 대조해야 한다. 그 과정에서 잘못 부여된 권한이 발견되면 관리 작업을 중단하고 해당 권한·접근 이력을 조사한다. 새 관리자 부여·회수는 권한 있는 서버/DB 절차에서 계정 ID 확인 후 수행한다. 이메일이나 프런트엔드 환경변수만으로 관리자를 부여하지 않는다.

격리 테스트 성공은 Lovable/Supabase 운영 환경에 마이그레이션이 실제 적용됐다는 증거가 아니다. 적용 버전·현재 관리자 명단·관리자 화면을 운영에서 확인하는 후속 작업은 [SC-001 기준선](./BASELINE.md)의 미확인 항목과 SC-010 감사에 연결한다.
