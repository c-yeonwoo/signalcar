# SC-046 · 이벤트·코호트·비용 측정 규약

확정일: 2026-09-29 · 상태: **계측 설계 완료, 수집·대시보드 구현 전**. [사전 실험 게이트](./HYPOTHESES.md)의 수치를 사후에 바꾸지 않는다. 이 문서는 현재 지표가 측정되었다는 뜻이 아니다.

## 식별자와 기록 단위

| 필드 | 규칙 |
|---|---|
| `event_id` | 발생 시 생성한 UUID. 전송 재시도에도 유지하며 서버가 유일 키로 중복 삽입을 막는다. |
| `project_id` | 한 구매 결정을 나타내는 UUID. 후보 수정·견적 재제출에도 유지한다. 다른 구매 계획은 새 ID다. 게스트가 로그인하면 원래 ID를 서버 사용자에 연결하고 이벤트를 복제하지 않는다. |
| `anonymous_id` | 게스트의 무작위 UUID. 기기 저장소가 지워지면 연결하지 않는다. 지문·광고 ID·연락처 해시로 복원하지 않는다. |
| `user_id` | 인증 후 내부 사용자 UUID. 계정 전환 시 이전 계정의 `project_id`를 현재 계정으로 합치지 않는다. |
| `session_id` | 방문 묶음용 무작위 UUID. 30분 비활동 뒤 교체. 핵심 전환의 고유 사용자 대용으로 쓰지 않는다. |
| `attempt_id` | 업로드·검토 요청·결제·파트너 전달의 각 시도 ID. 성공/실패/재시도를 구분한다. |
| 시간 | `occurred_at`과 서버 `received_at`을 UTC로 저장, KST 날짜로 리포트. 서버 확정 이벤트의 날짜는 서버 시간을 우선한다. 타임존/수집 지연을 기록한다. |

공통 이벤트는 `schema_version`, `event_name`, `event_id`, `occurred_at`, `received_at`, `source`(`client`/`server`/`manual_verified`), `project_id`(프로젝트 전에는 null), `anonymous_id` 또는 `user_id`, `session_id`, `attempt_id`(해당 시), `experiment_id`(해당 시), `properties`로 구성한다. 알려진 이벤트 이름·허용 속성만 수집하고 버전 변경 시 변환 또는 별도 집계한다. 개발/내부/자동화 트래픽은 `environment`와 `actor_type`으로 분리해 공식 지표에서 제외하되 원자료 삭제로 수치를 맞추지 않는다.

동일 `event_id`는 한 번만 집계한다. 동일 단계의 재방문 노출은 별도 이벤트지만 전환 분자는 프로젝트별 **첫 유효 완료 1건**이다. 수동 기록은 담당자·근거 ID를 남기고, 클라이언트 클릭보다 서버 장부가 우선한다. 클라이언트 시계가 어긋나거나 이벤트가 늦게 도착하면 두 시간과 수정 이력을 보존한다.

## 핵심 이벤트 사전

| 여정 | 노출/시작 | 유효 완료 | 완료의 증거와 구분 |
|---|---|---|---|
| 첫 방문 | `home_viewed`, `entry_option_viewed` | `entry_selected` | 세 진입점별 선택. 노출만으로 관심을 세지 않는다. |
| 구매 계획 | `project_start_clicked` | `project_created` | 저장 성공한 `project_id`. 빈 폼 열기는 제외. |
| 질문 | `question_step_viewed` | `required_answers_saved` | 필수 질문 4개 저장. `unknown_selected`는 응답으로 세되 임의 사실로 채우지 않는다. |
| 후보 | `shortlist_viewed` | `shortlist_saved` | 적격 후보 1~3대와 선택/탈락 이유가 프로젝트에 저장됨. `no_match_viewed`는 실패 맥락으로 별도 기록. |
| 비교 | `comparison_viewed` | `comparison_decision_saved` | 두 후보 이상 비교 후 중요 기준 또는 타협을 저장. 화면 체류만은 완료가 아니다. |
| 시승 | `test_drive_link_opened` | `test_drive_logged` | 사용자가 실제 시승일·확인 항목을 기록. 외부 예약 링크 클릭은 예약·시승 완료가 아니다. |
| 견적 | `quote_review_offer_viewed`, `quote_review_started` | `quote_review_submitted`, `quote_review_completed` | 제출은 접수 ID 발급, 완료는 검수자 결과 납품. OCR 성공이나 파일 업로드는 납품이 아니다. |
| 결제 | `checkout_started` | `payment_settled`, `payment_refunded` | 결제사/장부의 확정 사건. 클라이언트 성공 화면은 매출이 아니다. 취소·부분 환불은 금액을 함께 기록. |
| 연결 | `partner_option_viewed`, `partner_consent_opened` | `partner_lead_delivered`, `partner_response_confirmed`, `purchase_confirmed`, `partner_fee_settled` | 개별 동의 후 실제 전달, 파트너 응답, 고객 확인 계약, 정산 입금은 서로 다른 사건. |
| 안전·운영 | `price_correction_requested`, `privacy_delete_requested`, `support_case_opened` | `price_correction_resolved`, `privacy_delete_completed`, `support_case_resolved` | 처리 상태와 소요시간. 오류율은 실패 요청/전체 요청을 같은 기간·경로로 나눈다. |

각 단계에 `*_failed` 이벤트와 범주형 `reason_code`를 둘 수 있지만 견적 원문·민감한 오류 본문을 속성에 넣지 않는다. 노출은 화면이 실제 표시된 뒤 기록하며 동일 세션·단계의 반복 렌더는 노출 1건으로 묶는다. 완료는 저장 성공 후 기록하고, 수동 검수/결제/정산은 서버 또는 검수된 운영 기록이 확정한다.

## 분모·기간·집계

| 지표 | 분모 | 분자 | 관찰 기간·주의 |
|---|---|---|---|
| 7일 활성화 | 최초 `project_created`가 있는 적격 신규 프로젝트 | 생성 후 7×24시간 안에 `required_answers_saved`와 `shortlist_saved`를 모두 완료한 프로젝트 | 생성일 KST 주간 코호트. 7일 미경과 코호트는 제외하고 지연 수집은 잠정 표시. [사전 목표](./HYPOTHESES.md) 35%. |
| 활성 고객의 30일 진전 | 위 7일 활성화 프로젝트 중 생성 후 30일 관찰이 끝난 프로젝트 | 생성 후 30일 안에 `comparison_decision_saved`, `test_drive_logged`, `quote_review_completed`, `purchase_confirmed` 중 **하나 이상**을 완료한 프로젝트 | 같은 프로젝트가 여러 행동을 해도 분자 1. 클릭·업로드·상담 요청은 제외. [사전 목표](./HYPOTHESES.md) 25%. |
| 견적 제안→결제 | 실제 견적을 보유한 적격자에게 동일한 가격·범위를 제시한 고유 사람 수 | 그 제안에 귀속된 `payment_settled` 고유 사람 수 | 가격군별 분모/환불/납품/시간을 함께 보고, 친구·내부 테스트 제외. 20명 제안·5건 결제는 실험 목표. |
| 유료 납품·환불 | `payment_settled` 고유 주문 수 | `quote_review_completed` / 환불 확정 주문 수 | 제출·OCR 완료와 사람 검수 납품을 구분. 부분 환불은 원화 금액도 집계. |
| 연결 응답·계약·정산 | 동의한 `partner_lead_delivered` 고유 리드 수 | 각 단계의 실제 확정 고유 리드 수 | 파트너별·기간별. 응답률을 계약률이나 매출률로 바꾸지 않는다. |
| 가격/개인정보 안전 | 공개 가격 노출 또는 처리 요청의 고유 건수 | 정정 요청·중대 오표시·삭제 기한 초과 등 해당 사건 수 | 무사고는 접근/감사 범위가 확보된 기간에만 주장한다. |

베타의 100프로젝트는 적격성(구매 결정 참여, 첫 고객군, 프로젝트 생성 시점)을 생성 시 고정하고, 30일 관찰이 끝난 프로젝트만 판정 분모에 넣는다. 동일 사람이 여러 프로젝트를 만들면 프로젝트 지표와 사람 지표를 따로 내고 중복 비율을 밝힌다. 유입 채널별 성과는 최초 확인 가능한 유입만 귀속하고 `unknown`을 임의로 특정 채널에 배분하지 않는다. 가입·기기 변경으로 이어지지 않은 게스트는 추정 병합하지 않는다.

## 원가와 매출 장부

- 주문별 `gross_paid`, `refund_amount`, 결제 수수료, 검수자 작업분, CS 작업분, 자료 구입·OCR 비용, 파트너 정산 비용을 원화로 기록한다. 검수/CS는 시작·종료 또는 검증된 분 단위 작업 로그와 시간당 인건비 가정 버전을 남긴다.
- 건당 공헌이익 = 실제 수납액 − 환불 − 결제 수수료 − 해당 건 변동 인건비 − 해당 건 변동 도구/자료 비용. 공통 인프라·고정비는 별도 손익표에 배부 기준과 함께 표시한다. 무료 체험·쿠폰·실패 결제는 유료 판매로 세지 않는다.
- 제휴 매출은 `partner_fee_settled`의 실제 정산액에서 취소/환수액을 뺀다. 소개 클릭·리드 전달·파트너의 구두 계약 의사는 매출 0원이다.
- SC-007의 가격군과 SC-049/050의 확대 판단에 미납품·환불·실패 주문도 넣어 생존자 편향을 줄인다. 비용이 미기록이면 추정값의 범위와 미기록률을 함께 보이고 이익 확정치를 내지 않는다.

## 개인정보와 검증 절차

이벤트 속성에는 전화번호, 이름, 이메일, 견적 사진/원문, 정확한 주소·위치, 금융 신용정보를 넣지 않는다. 예산은 필요한 경우 구간만 사용한다. 서비스 제공에 필요한 원본 자료와 행동 분석 저장소를 분리하고, 동의·거부·삭제 요청을 프로젝트/계정 ID로 추적한다. 외부 분석 도구로 보내는 항목과 보관 기간은 출시 전 개인정보 검토(SC-014/015)를 거쳐 결정한다. 이 문서는 법적 적합성 판단이 아니다.

SC-047 구현 시 동일한 테스트 프로젝트 10개(게스트→로그인, 중복 전송, 지연 전송, 후보 수정, 외부 링크만 클릭, 업로드 실패, 결제 실패, 결제 성공 후 환불, 납품, 리드 전달 후 미응답)를 UI·서버 원장·집계에서 대조한다. 실제 사용자 데이터로 검증할 때는 동의 범위와 접근 권한을 먼저 확인한다. 계측이 없는 과거 기간은 0으로 채우지 않고 `미측정`으로 남긴다.
