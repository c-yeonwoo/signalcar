## 결정

현재는 **Lovable 웹 앱 + Supabase DB·Storage·Auth + GitHub Actions 수집 워커**를 유지한다. `main`은 변경을 모으는 브랜치이고, **Lovable에 Git 커밋이 동기화되는 것과 공개 사이트에 Publish하는 것은 별개**다. 기능 작업은 완료 순서대로 `main`에 반영하되, 고객에게 보이는 릴리스는 검증된 커밋을 선택해 Publish한다. DB 변경과 워커 재개도 별도 단계로 취급한다. 지금 호스팅을 이전하면 원인 규명이 어려워지므로 실제 배포 경로와 운영 데이터부터 확정한다.

| 환경 | 목적 | 최소 요건 |
|---|---|---|
| 로컬·격리 DB | SQL 전체 재적용, RLS 및 기능 테스트 | 운영 키·고객 데이터 사용 금지 |
| 스테이징 | 실제 배포 순서와 UI·Auth·파일·워커 스모크 | 별도 Supabase 프로젝트, 별도 Lovable 미리보기/프로젝트 또는 동등한 분리 환경. 개인정보·실제 메일 발송 금지 |
| 운영 | 제한적 공개와 관측 | 실제 URL·연결 프로젝트·마이그레이션 이력·복구 수단을 릴리스 기록에 고정 |

Lovable의 [GitHub 연동](https://docs.lovable.dev/integrations/github)과 [Publish 동작](https://docs.lovable.dev/features/publish), Supabase의 [배포 개요](https://supabase.com/docs/guides/deployment)를 기준으로 한다. 스테이징 환경을 만들 수 없으면 운영 DB에 직접 실험하지 않고 격리 DB와 Lovable 미리보기에서 검증 가능한 범위만 진행한다.

## 현재 확인된 배포 상태와 미확인 항목

- `main`과 원격 `main`은 확인 시 `f75496b`였다. 기존 미커밋 `src/routeTree.gen.ts` 변경은 이번 작업 범위 밖이다. 저장소는 공개 상태이므로 운영 비밀값을 Git에 넣지 않는다.
- `supabase/migrations/`에는 26개 SQL이 있으며 마지막은 `20260929090000_pause_catalog_price_writes.sql`이다. **운영 DB에 어느 파일까지 적용됐는지는 확인하지 못했다.** 기존 `supabase/MIGRATION.md`의 “미적용분”은 실제 이력의 증거가 아니다.
- `ingest-loop.yml`은 매일 06:00 KST 실행 설정이지만 2026-09-29 확인 시 GitHub에서 `disabled_inactivity`였다. 마지막으로 확인 가능한 성공 실행은 09-15의 오래된 커밋이었다. 워크플로에는 의존성 설치 단계가 없고 Bun은 `latest`라 재실행 가능성이 낮다. GitHub Secrets의 존재·값은 확인하지 못했다.
- 코드·예시의 `signalcar.lovable.app`은 확인 시 404(`project_not_found`)였다. 실제 Publish URL, 활성 커밋, 공개 범위와 커스텀 도메인은 **미확인**이다. 운영 로그·백업·Storage 객체·DB 쓰기 작업 상태도 미확인이다.
- 가격·견적 접수 화면은 앱에서 임시 게이트를 두고 있다. 이것을 운영 권한 정책·데이터의 검증으로 간주하지 않는다.

## 배포 전 관문: 운영 기준선 확보

다음 증거가 채워지기 전에는 운영 DB에 `db push`를 하지 않고, 수집 워커를 켜거나 가격·견적 접수를 공개하지 않는다.

1. **배포 대상:** Lovable 프로젝트의 연결 브랜치, 실제 Publish URL·현재 릴리스 커밋·도메인, 운영 Supabase 프로젝트 ref 및 스테이징과의 분리를 기록한다. URL은 공개 접속으로 재확인한다.
2. **DB 이력:** 권한 있는 운영자 한 명이 `supabase migration list`와 `supabase_migrations.schema_migrations`를 읽기 전용으로 확인해 파일 26개와 대조한다. `supabase db push --dry-run`으로 예정 SQL을 확인한다. 누락·순서 차이·대시보드 수동 변경이 있으면 원인을 조사하고 스테이징에서 재현한다. 과거 7월 마이그레이션이 미적용이면 신규 9월 SQL까지 한 번에 운영에 넣지 않는다.
3. **쓰기 경로:** DB cron, Edge Functions, GitHub Actions, 메일 발송, 수집 작업 각각의 활성 상태와 마지막 실행을 확인한다. 특히 카탈로그 가격 자동 쓰기와 프로모션·알림 잡은 코드의 기본값만으로 운영 중단 여부를 판단하지 않는다.
4. **복구:** 배포 직전 DB 백업 시각·보관 기간·복구 담당자를 기록하고 격리 프로젝트로 복구 연습을 한다. Supabase DB 백업에는 Storage 객체가 포함되지 않으므로 버킷 정책·객체 보존/복사 경로도 별도로 점검한다. 개인정보 파일은 접근을 최소화한다. [Supabase 백업 문서](https://supabase.com/docs/guides/platform/backups)
5. **비밀값:** 공개 저장소·Git 이력에서 비밀값 유출 여부를 검사하고, 발견 시 재발급한다. 서비스 역할 키는 클라이언트·`VITE_` 환경 변수·빌드 산출물에 넣지 않는다. GitHub Actions 시크릿은 전용 Environment에 배치하고 접근자를 제한한다.

## 릴리스 절차

### 1. 코드 릴리스 후보

- 대상 커밋 SHA와 변경된 마이그레이션, 앱 화면, 워커 잡을 한 릴리스 기록에 묶는다. `main` 반영 직후 자동 공개를 가정하지 않는다.
- 깨끗한 체크아웃에서 `npm ci`, `npx tsc --noEmit`, `bun test`, `npm run build`를 실행한다. 수집 워커는 의존성 설치 후 번들 또는 최소 실행 검증을 별도로 한다. 격리 DB를 초기화하고 모든 SQL 마이그레이션과 `supabase/tests/`의 권한·가격·견적 문서 테스트를 실행한다. 테스트가 실패한 SHA는 Publish하지 않는다.
- 스테이징에서 익명·일반 계정·관리자 역할별로 홈/탐색, 로그인, 빈 데이터/DB 오류, 타인 견적 파일·관리 쓰기 거부, 견적 접수 차단, 가격 근거 표시를 확인한다. 스테이징 데이터에는 실제 고객 파일을 복제하지 않는다.

### 2. 운영 변경 창

1. 변경 시작 시각, 담당자, SHA, 운영 URL, DB 프로젝트, 백업 식별자, 롤백 담당자를 기록한다. 새 수집·메일 잡을 중지하고 진행 중 작업이 끝났는지 확인한다.
2. **DB 먼저:** 운영에 Supabase GitHub 통합이 이미 마이그레이션을 적용한다면 CLI로 중복 적용하지 않는다. 그렇지 않다면 지정된 한 명이 migration list와 dry-run을 재확인한 뒤 `supabase db push`로 적용한다. 순서를 바꾸거나 SQL Editor에서 임의 파일을 실행하지 않는다. [Supabase 마이그레이션 안내](https://supabase.com/docs/guides/deployment/database-migrations)
3. 앱 Publish 전에 읽기 전용 운영 스모크로 핵심 테이블·RLS·Storage 비공개 정책·중단해야 할 작업의 상태를 확인한다. 예상 밖의 권한 노출이나 데이터 변경이 있으면 여기서 멈춘다.
4. Lovable이 대상 SHA를 동기화한 것을 확인한 뒤 Publish하고, **실제 운영 URL**에서 로그인·탐색·가격 출처/미확인 표시·비공개 경로·모바일 화면을 확인한다. 테스트는 최소 권한의 전용 계정과 비식별 테스트 데이터로 수행한다.
5. 첫 24시간은 5xx/클라이언트 오류, 인증 실패, DB 오류, Storage 접근 거부/허용, 배포 버전, 데이터 변경량을 집중 관측한다. 고객 접수·결제·제휴 전달은 각각의 제품·운영 게이트가 끝나기 전까지 계속 닫아 둔다.
6. 워커는 별도 릴리스로 다룬다. Bun 버전 고정, `bun install --frozen-lockfile`, GitHub Environment/동시 실행 제한, 시크릿 확인을 마친 뒤 읽기 전용 또는 좁은 단일 잡을 `workflow_dispatch`로 검증한다. 쓰기량·오류·출처를 확인하고 나서 일일 스케줄을 다시 켠다. `--force` 실행은 금지한다.

### 3. 실패 시 중단·복구

| 징후 | 즉시 조치 | 복구 |
|---|---|---|
| 타인 견적/관리 데이터 접근, 검증 전 가격 공개, 예상 밖 메일·가격 쓰기 | 해당 화면·잡 차단, 워커 중지, 접근 기록 보존 | 권한/데이터 원인 확인 후 수정 마이그레이션과 재검증 |
| 앱 5xx, 로그인·탐색 주요 여정 실패 | Publish 확대 중단 | 이전 정상 코드로 **새 커밋**을 만들고 동기화·재Publish. Lovable 연결 브랜치의 공개 이력은 force push/rebase/amend 하지 않음 |
| SQL 실패·데이터 손상 | 쓰기 중지, 변경 구간과 영향 행 보존 | 데이터 보존형 전진 수정 우선. 삭제·손실은 백업을 별도 프로젝트에 복원해 필요한 행만 검증 후 복구. 운영 전체 복원은 다운타임·복원 시점 이후 데이터 손실을 계산한 마지막 수단 |
| 수집 폭주·중복 행 | Action 비활성화, DB 잡 중지 | 원인·중복 범위 감사 후 제한적으로 재실행 |

DB 변경은 일반적으로 앱 코드처럼 안전하게 되돌릴 수 없다. 따라서 스키마는 기존 앱과 새 앱 모두 작동하도록 추가→전환→정리 순서로 변경하고, destructive SQL은 별도 릴리스와 복구 연습을 요구한다.
